### 발생한 문제 및 해결

#### 1. 마지막 기억 값을 삭제해도 key가 남을 수 있음

#### 원인

예를 들어 다음과 같이 하나의 값만 저장되어 있을 때:

```text
favorite_languages
└── Python
```

`Python`을 삭제하면 `favorite_languages`에 더 이상 값이 없는데도 `key`만 남을 수 있었음

#### 해결

`delete_memory_value()`에서 값을 삭제한 후 해당 `memory_id`에 남아 있는 값의 개수를 확인하도록 수정함

```sql
SELECT COUNT(*)
FROM memory_values
WHERE memory_id = ?
```

남아 있는 값이 `0`개라면 `memories` 테이블에서도 해당 `key`를 삭제하도록 함

처리 흐름:

```text
특정 value 삭제
        ↓
남아 있는 value 개수 확인
        ↓
    0개인가?
    /       \
    Yes        No
    ↓          ↓
key 삭제   key 유지
```

---

#### 2. DB 구조 변경 후 기존 코드와 반환 형태가 달라짐

#### 원인

장기 기억 값을 DB에서 각각 별도의 행으로 저장하면서, 기존 코드가 기대하던:

```text
favorite_languages: Python, Java
```

형태와 DB의 실제 저장 형태가 달라짐

#### 해결

`get_memories()`에서 같은 `key`에 해당하는 값들을 Python 리스트로 모은 후:

```python
", ".join(values)
```

를 사용하여 다시 하나의 문자열로 결합하도록 함

이를 통해 DB에서는 정규화된 구조를 유지하면서 기존 코드와의 호환성도 유지함

---

### 이 날의 결과

장기 기억에서 하나의 `key`에 여러 값을 독립적으로 저장하고 삭제할 수 있도록 개선하고, 마지막 값 삭제 시 불필요한 `key`가 남는 문제를 해결하면서 기존 코드와의 호환성을 유지함

### 발생한 문제 및 해결

#### 1. 외래 키 활성화 후 장기 기억 추가 실패

DB 연결을 다음과 같이 변경함
```python
def connect_db():
    conn = sqlite3.connect(DB_PATH)
    conn.execute("PRAGMA foreign_keys = ON")
    return conn
```

이후 새로운 장기 기억을 저장하려고 하면 다음 오류가 발생함
```python
sqlite3.IntegrityError: FOREIGN KEY constraint failed
```

#### 원인

SQLite의 외래 키 정보를 직접 확인함

```sql
PRAGMA foreign_key_list(memory_values)
```

확인 결과 `memory_values.memory_id`가 정상적인 `memories` 테이블이 아니라:

```text
old_memories
```

를 참조하고 있었음

즉 실제 구조가:

```text
memory_values.memory_id
        ↓
old_memories.id
```

로 되어 있었음

기존 `migrate_memories()`에서:

```sql
ALTER TABLE memories
RENAME TO old_memories
```

방식을 사용했던 것이 원인이었음

#### 해결

DB를 바로 삭제하거나 초기화하지 않고 먼저 현재 데이터를 확인함

`memories.id`와 `memory_values.memory_id`가 서로 정상적으로 대응하고 있음을 확인한 후 `memory_values` 테이블을 재구성함

외래 키를:

```text
memory_values.memory_id
        ↓
    memories.id
```

로 복구함

최종적으로:

```sql
PRAGMA foreign_key_list(memory_values)
PRAGMA foreign_key_check
```

를 이용해 검증함

결과:

```text
FOREIGN KEY → memories
CHECK → []
```

외래 키 위반이 존재하지 않는 것을 확인함

------------------------------------------------------------------------

#### 2. 기존 마이그레이션 방식에서 같은 외래 키 문제가 재발할 가능성

#### 원인

현재 DB만 복구하면 기존 `migrate_memories()`를 다른 오래된 DB에 적용했을 때 같은 문제가 다시 발생할 가능성이 있었음

#### 해결

기존의:

```sql
ALTER TABLE memories
RENAME TO old_memories
```

방식을 제거함

기존 데이터를 먼저 읽어둔 후 새로운 구조의 테이블을 생성하여 데이터를 이전하도록 마이그레이션 방식을 변경함

기존 `id`, `created_at`, `updated_at`도 보존하도록 했으며, 예상하지 못한 기존 `memory_values` 데이터가 존재할 경우 임의로 삭제하지 않고 마이그레이션을 중단하도록 안전장치를 추가함

------------------------------------------------------------------------

#### 3. 기억 값의 대소문자 중복 가능성

#### 원인

기존 구조에서는 다음 값들이 서로 다른 값으로 저장될 가능성이 있었음

```text
Python
python
PYTHON
```

#### 해결

`add_memory_value()`에서 기존 값을 확인할 때:

```python
LOWER(value) = LOWER(?)
```

조건을 사용하도록 변경함

따라서 대소문자만 다른 동일한 값이 중복으로 추가되지 않도록 함

`delete_memory_value()`에도 같은 방식을 적용하여 저장된 값이 `Rust`여도:

```text
Rust
rust
RUST
```

중 어느 형태를 사용해도 삭제할 수 있도록 함

------------------------------------------------------------------------

#### 4. DB 작업 도중 오류가 발생할 경우의 안정성

#### 원인

DB 작업이 여러 단계로 이루어져 있을 때 중간에 오류가 발생하면 일부 작업만 수행된 상태가 될 가능성이 있었음

특히 `save_memory()`는 기존 값을 삭제한 뒤 새로운 값을 저장하기 때문에 중간 오류에 대한 처리가 중요함

#### 해결

`add_memory_value()`, `save_memory()`, `delete_memory_value()`에 다음 구조를 적용함

```python
try:
    ...
    conn.commit()

except Exception:
    conn.rollback()
    raise

finally:
    conn.close()
```

모든 작업이 성공하면 `commit()`하고, 중간에 오류가 발생하면 `rollback()`하도록 함

또한 성공 여부와 관계없이 `finally`에서 DB 연결을 종료하도록 함

#### 5. 최근 대화 기록 개수가 코드에 고정됨

기존에는:

```python

```

처럼 최근 대화 기록의 개수가 Python 코드에 직접 작성되어 있었음

설정값을 변경하려면 코드를 수정해야 하는 문제가 있었음

을 추가함

이후 `chat_service.py`에서는 환경변수에서 가져온 값을 사용하도록 변경함

또한:

```env
CHAT_HISTORY_LIMIT=-10

```

같은 잘못된 설정으로 프로그램이 종료되지 않도록 검증 기능을 추가하고, 잘못된 경우 기본값 `20`을 사용하도록 함

#### 7. 자동 제목 생성 실패에 대한 예외 처리

자동 제목 생성은 일반 대화 기능을 보조하는 부가 기능이므로 제목 생성 과정에서 오류가 발생하더라도 일반 채팅이 중단되지 않도록 예외 처리를 추가함

자동 제목 생성 및 저장 부분을 `try / except`로 처리하여 오류가 발생하면 다음과 같은 로그만 출력하도록 구성함

```text
[Session] 자동 제목 생성 실패: ...
```

제목 생성에 실패하더라도 이미 생성된 일반 AI 응답은 정상적으로 저장되고 사용자에게 출력되도록 함

이를 통해 부가 기능의 오류가 챗봇의 핵심 대화 기능에 영향을 주지 않도록 구조를 개선함

### 발생한 문제 및 해결

#### 1. 기존 DB에 세션 제목 컬럼을 추가해야 하는 문제

#### 원인

기존 `chat_sessions` 테이블은 이미 생성되어 있었기 때문에 테이블 생성문에 단순히 `title` 컬럼을 추가하더라도 기존 DB의 테이블 구조는 변경되지 않음

`CREATE TABLE IF NOT EXISTS`는 테이블이 이미 존재하면 새로운 테이블을 다시 생성하거나 기존 구조를 수정하지 않기 때문임

#### 해결

`migrate_chat_sessions_title()` 함수를 추가하여 기존 `chat_sessions` 테이블의 컬럼을 확인하도록 함

`title` 컬럼이 없는 경우에만 `ALTER TABLE`을 이용해 컬럼을 추가하고, 이미 존재하는 경우에는 마이그레이션을 수행하지 않도록 구성함

이를 통해 기존 데이터와 세션을 유지하면서 새로운 제목 기능을 안전하게 추가할 수 있게 됨

------------------------------------------------------------------------

#### 2. 자동 제목 생성 실패가 일반 대화에 영향을 줄 수 있는 구조

#### 원인

자동 제목 생성 과정에서도 별도의 API 요청과 DB 저장 작업이 발생함

따라서 제목 생성 과정에서 API 오류나 예상하지 못한 예외가 발생하면 일반 AI 응답이 정상적으로 생성되었더라도 이후 처리 과정이 중단될 가능성이 있었음

자동 제목은 부가 기능이므로 해당 기능의 실패 때문에 핵심 기능인 일반 대화까지 실패하는 것은 적절하지 않음

#### 해결

자동 제목 생성 및 저장 과정을 별도의 `try / except`로 처리함

제목 생성에 실패하면 오류 내용을 로그로 출력하되 일반 대화 흐름은 계속 진행하도록 구성함

이를 통해 자동 제목 기능과 일반 대화 기능의 실패 범위를 분리함

------------------------------------------------------------------------

```python
def get_latest_chat_session_id():
    conn = connect_db()
    cursor = conn.cursor()

    try:
        cursor.execute("""
            SELECT id
            FROM chat_sessions
            ORDER BY id DESC
            LIMIT 1
        """)

        row = cursor.fetchone()

        if row is None:
            return None

        return row[0]

    finally:
        conn.close()
```

### 발생한 문제 및 해결

#### 1. 현재 사용 중인 세션을 삭제한 이후의 세션 상태 처리

#### 원인

특정 세션을 단순히 삭제하는 것만으로는 현재 사용 중인 세션을 삭제했을 때 이후 어떤 세션에서 대화를 계속할지 결정할 수 없음

`chat_state.current_session_id`는 외래 키의 `ON DELETE SET NULL` 설정으로 인해 현재 세션 삭제 시 자동으로 `NULL`이 되지만, 다른 세션이 남아 있더라도 자동으로 해당 세션을 선택하지는 않음

따라서 현재 세션을 삭제한 이후에도 다른 대화 세션이 존재한다면 새로운 현재 세션을 결정하는 처리가 필요함

#### 해결

세션을 삭제하기 전에 기존 `current_session_id`를 확인하고, 삭제한 세션이 현재 세션이었던 경우 남아 있는 가장 최근 세션을 조회하도록 함

이를 위해 `get_latest_chat_session_id()`를 추가했으며, 남아 있는 세션이 존재하면 `set_current_session_id()`를 이용하여 해당 세션으로 자동 이동하도록 구성함

남아 있는 세션이 없다면 `ON DELETE SET NULL`에 의해 설정된 `NULL` 상태를 그대로 유지하도록 함

#### 2. 전체 대화 삭제와 특정 대화 세션 삭제 명령어의 구분


정확히 `대화삭제`와 일치하는 기존 명령어를 먼저 처리한 뒤, 그 아래에서 `대화삭제`로 시작하는 특정 세션 삭제 명령어를 처리하도록 순서를 구성함

#### 2. 제목과 메시지 내용을 이용한 세션 검색 구현

검색 조건은 다음과 같은 방식으로 구성함

```sql
WHERE LOWER(COALESCE(chat_sessions.title, '')) LIKE ?
    OR EXISTS (
        SELECT 1
        FROM messages
        WHERE messages.session_id = chat_sessions.id
            AND LOWER(COALESCE(messages.content, '')) LIKE ?
    )
```

### 발생한 문제 및 해결

#### 1. 검색 결과의 메시지 개수 계산 방식

#### 원인

검색 결과에 메시지 개수를 추가하면서 검색에 사용한 `messages` 테이블을 그대로 `COUNT()`할 경우 검색 조건에 일치한 메시지만 계산될 수 있음

하지만 검색 결과에서 표시하려는 값은 검색어가 발견된 메시지 개수가 아니라 해당 세션에 저장된 전체 메시지 개수임

#### 해결

메시지 검색과 전체 메시지 개수 계산을 분리함

검색어가 포함된 메시지의 존재 여부는 `EXISTS`를 이용하여 확인하고, 전체 메시지 개수는 별도의 서브쿼리에서 `COUNT(*)`를 이용하여 계산하도록 구성함

```sql
(
    SELECT COUNT(*)
    FROM messages
    WHERE messages.session_id = chat_sessions.id
) AS message_count
```

이를 통해 메시지 내용으로 세션을 검색하면서도 검색 결과에는 해당 세션의 전체 메시지 개수를 정확하게 표시할 수 있게 됨

#### 2. 메시지 미리보기에서 실제 검색어를 확인할 수 없는 문제

#### 원인

처음 구현한 메시지 미리보기는 검색된 메시지의 처음부터 일정 길이만큼만 표시하는 방식이었음

```python
preview = content[:preview_length]
```

따라서 검색어가 긴 메시지의 중간이나 뒤쪽에 존재하면 검색에는 성공하지만 미리보기에서는 실제 검색어가 표시되지 않는 문제가 있었음

실제로 `FileNotFoundError`를 검색했을 때 검색어 대신 AI 답변의 처음 부분만 표시됨

#### 해결

`find()`를 이용하여 전체 메시지에서 검색어가 시작되는 위치를 찾고 해당 위치를 기준으로 앞뒤 문맥을 가져오도록 변경함

```python
match_index = content_lower.find(query_lower)
```

검색어 앞뒤에 일정 길이의 문맥을 포함하고 생략된 부분에는 `...`을 표시하도록 구성함

그 결과 검색 결과가 다음과 같이 개선됨

```text
└ AI: ...load(file) print(data) except FileNotFoundError: print("JSON 파일을 찾을 수 없습니다.")...
```

이제 검색 결과만 확인해도 어떤 메시지의 어떤 내용 때문에 해당 세션이 검색되었는지 파악할 수 있게 됨

- 기억 디버그: ON

#### 1. Windows에서 Asia/Seoul 시간대를 찾지 못하는 문제

#### 원인

Python의 `zoneinfo.ZoneInfo("Asia/Seoul")`을 사용하여 한국 시간으로 변환하려 했지만 Windows 환경에서 시간대 데이터가 설치되어 있지 않아 다음 오류가 발생함

```python
ZoneInfoNotFoundError: 'No time zone found with key Asia/Seoul'
```

내부적으로 필요한 `tzdata` 패키지도 설치되어 있지 않음

#### 해결

가상환경에 `tzdata` 패키지를 설치함

```powershell
pip install tzdata
```

설치 후 `ZoneInfo("Asia/Seoul")`이 정상적으로 동작했고, UTC로 저장된 대화 생성 시간이 한국 시간으로 올바르게 표시되는 것을 확인함

새로운 의존성을 프로젝트에 반영하기 위해 `requirements.txt`도 다시 생성함

```powershell
pip freeze > requirements.txt
```

#### 2. 대화 메시지 수정 시 SQLite 바인딩 개수 오류

#### 원인

`대화수정` 기능을 테스트하는 과정에서 다음 오류가 발생함

```python
Incorrect number of bindings supplied. The current statement uses 2, and there are 3 supplied.
```

메시지 수정 SQL문에는 두 개의 `?`만 존재했지만, 실제로는 `content`, `message_id`, `session_id` 세 개의 값을 전달하고 있었음

#### 해결

수정할 메시지가 지정한 세션에 실제로 속해 있는지도 함께 확인할 수 있도록 SQL문의 조건에 `session_id`를 추가함

```sql
UPDATE messages
SET content = ?
WHERE id = ?
    AND session_id = ?;
```

SQL문의 세 개의 `?`와 전달하는 세 개의 값이 일치하도록 수정한 뒤 메시지가 정상적으로 수정되는 것을 확인함

대화 요약을 데이터베이스에 저장하고 재사용할 수 있도록 개선하고, 메시지가 추가되거나 수정되면 기존 요약을 자동으로 무효화하여 실제 대화 내용과 요약의 일관성을 유지할 수 있도록 구현함

사용자가 변경한 설정을 `settings.json`에 저장하고 프로그램 시작 시 다시 불러오도록 구현하여 프로그램을 재실행해도 설정이 유지되도록 개선함

### 발생한 문제 및 해결

#### 1. 현재 세션이 없을 때 messages 변수가 생성되지 않을 가능성

#### 원인

`messages` 변수가 `if session_id is not None:` 내부에서 생성되고 있어 현재 세션이 없는 상태에서 함수가 실행될 경우 `messages`가 정의되지 않은 상태로 사용될 가능성이 있었음

#### 해결

`generate_chat_response()` 함수 초기에 `messages = []`를 추가하여 세션 존재 여부와 관계없이 `messages` 변수가 항상 초기화되도록 수정함

수정 후 프로그램이 정상적으로 시작되는 것을 확인함

------------------------------------------------------------------------

#### 2. 명령어 모듈 분리 과정에서 기존 코드와 새 코드가 일시적으로 중복됨

#### 원인

- 기존 명령어 코드를 바로 삭제한 상태에서 새 모듈에 문제가 발생하면 원래 기능으로 되돌리기 어려울 수 있었음
- 여러 명령어를 한 번에 이동할 경우 어떤 모듈에서 문제가 발생했는지 확인하기 어려울 수 있었음

#### 해결

- 새 명령어 모듈을 먼저 생성하고 import 테스트를 진행함
- `command_handler.py`에서 새 모듈을 기존 명령어 코드보다 먼저 호출하도록 연결함
- 실제 명령어가 정상적으로 동작하는 것을 확인한 뒤 기존 중복 코드를 제거함
- 설정, 도움말, 삭제 확인, 장기 기억, 대화 관리 순서로 기능을 단계적으로 분리함

#### 3. 삭제 확인 상태를 여러 명령어 모듈에서 공유해야 하는 문제

#### 원인

- 기존에는 `pending_delete_command`와 `pending_delete_target`이 `command_handler.py` 내부에 존재했음
- 대화 명령어와 장기 기억 명령어를 각각 별도 파일로 분리하면서 삭제 확인 상태를 한 곳에서 관리할 필요가 생김

#### 해결

- `commands/delete_confirmation.py`를 별도로 생성함
- 삭제 대기 상태와 확인/취소 처리를 해당 모듈에서 관리하도록 변경함
- `set_pending_delete()`를 제공하여 대화 및 장기 기억 명령어가 공통 삭제 확인 기능을 사용할 수 있도록 구성함

오래된 대화를 배치 단위로 자동 요약하고 최근 대화 및 아직 요약되지 않은 메시지와 함께 AI의 대화 맥락으로 활용하는 컨텍스트 관리 구조를 구현함

또한 체크포인트를 이용하여 이미 요약된 메시지의 중복 처리를 방지하고, 요약된 메시지가 수정될 경우 기존 컨텍스트 요약을 무효화하여 실제 대화 내용과의 일관성을 유지할 수 있도록 개선함

기존 `command_handler.py`에 집중되어 있던 명령어 처리 기능을 도움말, 설정, 삭제 확인, 장기 기억, 대화 관리 모듈로 분리하고, `command_handler.py`는 각 모듈로 사용자 입력을 전달하는 라우터 역할만 담당하도록 구조를 개선함

모듈 분리 후 각 명령어와 일반 AI 대화를 다시 테스트하여 기존 기능이 정상적으로 동작하는 것을 확인함
